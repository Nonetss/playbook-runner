`apps/ansible/app/services/ansible/materialize.py` monta esto para cada ejecución y lo borra siempre al terminar, también tras un error o una cancelación:

```text
$RUN_SCRATCH_DIR/<playbook>-<id>/
  keys/<host>-*.key          # 0600, una por host
  inventory/hosts.json       # lo escribe ansible-runner
  secret-vars.yml            # 0600, solo si hay secretos
  <playbook>-<hash>.yml      # inline: el contenido guardado
  project/                   # Git: el árbol del commit fijado
  runner-ansible.cfg         # Git: vacío, para anular el del repositorio
```

## Inline y Git

| | Inline | Git |
| --- | --- | --- |
| Ficheros disponibles | Solo el playbook | Todo el árbol del commit |
| Roles, `files/`, `templates/`, `import_playbook` | No | Sí |
| Edición en la app | Sí | Solo lectura, salvo sus variables secretas |
| Commit | No aplica | `last_commit_sha`, registrado en `job_runs.commit_sha` |
| `ansible.cfg` | No hay | Se ignora con `ANSIBLE_CONFIG` |

## Destino

`play_targets.py` reescribe a `all` el `hosts` de cada play, en la copia y a nivel de texto, para conservar comentarios y `!vault`. Sigue `import_playbook` dentro del proyecto, salvo rutas con plantillas. Lo que no puede leer como YAML lo deja tal cual, para que Ansible informe con sus propias palabras.

El inventario es plano: `{"all": {"hosts": {...}}}`. La conexión va por host: `ansible_host`, `ansible_user` de la credencial, `ansible_port` y `ansible_ssh_private_key_file`.

Consecuencias, todas probadas:

- Todas las plays corren en todos los hosts elegidos, `hosts: localhost` incluido.
- `group_names` vale `['ungrouped']`, y `groups['x']` no existe aunque se haya elegido un grupo en la app.
- De `group_vars/` junto al playbook solo se aplica `all`. `host_vars/` con el nombre del dispositivo sí funciona.

## Entorno

- **Colecciones:** las del paquete `ansible` (`apps/ansible/pyproject.toml`) más `infisical.vault`, fijada en `apps/ansible/Dockerfile` y `Dockerfile.dev`. No se pueden añadir otras por ejecución.
- **Usuario:** UID 10001, sin `sudo` en la imagen. Afecta a lo que corre con `delegate_to: localhost`.
- **Claves de host:** según `SSH_HOST_KEY_POLICY` (`ssh_policy.py`), por defecto `accept-new`.

## Cancelación

Una ejecución interactiva se cancela al cerrar el flujo, y la lanzada a mano desde un job con `jobs.runs.cancel`; una programada [no se puede cancelar](catalog:problemas/job-sin-cancelacion). En ambos casos una señal hace que `serverStream` cancele la llamada al momento, también durante una tarea silenciosa, y el ejecutor para Ansible, mata lo que quede y borra las claves.

Cancelar no deshace nada: los cambios aplicados se quedan, y un comando ya lanzado en un host puede seguir allí aunque muera su `ssh`. El backend da la ejecución por terminada en cuanto cancela la llamada, hasta 30 s (`CANCEL_WAIT_S`) antes de que Ansible pare del todo, así que relanzar un job enseguida puede solaparse con la anterior en los mismos hosts.

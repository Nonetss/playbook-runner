## Why

Long-running executions fail with `gRPC INTERNAL: Received RST_STREAM with code 2 (Internal server error)` even though they are well inside the one-hour `RUN_TIMEOUT_MS`. Ansible only emits events when a task starts or finishes, so a slow task such as a package upgrade leaves the HTTP/2 stream with no traffic for minutes. That stream goes backend → gateway (Caddy, `:50050`) → Ansible. Neither side configures HTTP/2 keepalive, and the backend's `@grpc/grpc-js` runs on Bun's `node:http2`, which does not reliably keep idle streams open. The result is a reset stream, a `failed` run and an operator who can't tell whether the hosts finished the work.

## What Changes

- Configure HTTP/2 keepalive on the gRPC channel the backend opens (`getClient` in `packages/grpc`), with intervals and timeouts as named constants.
- Configure the Ansible gRPC server (`python/grpc-toolkit`) to accept those keepalive pings while a call is open, instead of answering with `GOAWAY too_many_pings`.
- Add an application-level `heartbeat` frame to the four run response messages (`RunBundleResponse`, `RunPingResponse`, `RunCommandResponse`, `RunScriptResponse`) in `proto/run.proto`. The Ansible service sends it whenever a run has produced no frame for `RUN_HEARTBEAT_INTERVAL_S` (default 15 s), so the stream always carries data, whatever the transport, proxy or runtime.
- The backend drops `heartbeat` frames in `toEventIterator` and in the job executor. They never reach the browser, the live-run registry or `job_runs.events`.
- When a stream is reset anyway, the run's error message says that the connection to the Ansible service was lost and that the hosts may have finished the work. The opaque gRPC detail alone is no longer the whole message.

No breaking change: the new `oneof` field is additive and both sides are deployed together.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `run-lifecycle`: adds a requirement that execution streams stay alive while Ansible is silent (transport keepalive plus heartbeat frames that consumers ignore), and that a lost stream is reported as a connection loss.

## Impact

- `proto/run.proto`: new `Heartbeat` message and a `heartbeat` field in each run response `oneof`. TypeScript and Python stubs are regenerated by the existing `generate-grpc` steps.
- `packages/grpc/src/client.ts`: channel options for keepalive.
- `python/grpc-toolkit/grpc_toolkit/server.py`: server options for keepalive.
- `apps/ansible/app/grpc/services/runner.py` (`_stream_runner`/`_serve`) and `apps/ansible/app/core/config.py` (`run_heartbeat_interval_s`).
- `packages/api/src/v1/run/proto.ts` (`toEventIterator`) and `packages/api/src/v1/jobs/executor.ts` (frame loop and error message).
- `apps/gateway/Caddyfile`: no change. `flush_interval -1` already forwards each frame immediately, and `reverse_proxy` sets no stream timeouts. The change is verified through the gateway, which is the default path.
- No database, migration or frontend changes. The browser leg already has oRPC event-iterator keepalive.

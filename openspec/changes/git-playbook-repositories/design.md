## Context

- Playbooks live in `playbooks.content` (one YAML document). `run/resolve.ts`
  sends `{ name, content }` in `RunBundleRequest.playbook`; the Ansible service
  (`materialize.py`) writes it to `<run_dir>/<name>-<hash>.yml` and runs
  `ansible-runner` with `project_dir = run_dir`. Nothing else from the project
  (roles, templates, vars) can exist next to it.
- The backend image is Bun-only (no `git`, no writable state). The Ansible
  service already owns persistent state (`STATE_DIR`, `known_hosts`), a scratch
  dir per run, SSH key handling, `SSH_HOST_KEY_POLICY` and the concurrency cap.
- Jobs reference `playbooks.id` (`on delete set null`); run history lives in
  `job_runs`.
- Migrations are generated by the user, never by the agent.

## Goals / Non-Goals

**Goals:**
- Register Git repositories (public HTTPS or SSH with a stored credential).
- Manual sync that discovers playbooks and exposes them as read-only playbooks
  with stable ids, so jobs keep working across syncs.
- Runs of Git playbooks execute inside a checkout of the synced commit, so
  multi-file Ansible projects work.
- Record the commit each run used.

**Non-Goals:**
- Webhooks, polling or auto-sync on a schedule.
- HTTPS username/token authentication.
- Installing `requirements.yml` roles/collections from Galaxy.
- Editing Git playbooks in the UI or pushing back to the repository.
- Multiple refs per repository (one branch per repository record).

## Decisions

### 1. Git operations run in the Ansible service, not the backend
The Ansible service already has `STATE_DIR`, SSH key materialization and the
host-key policy; the backend image has no `git` and is stateless. A new unary
RPC `SyncRepository(url, branch, subdir, ssh_key?) → { commit, files[] }` keeps
the backend a pure gRPC client.
*Alternative*: `isomorphic-git` in the backend — rejected: adds state and SSH
handling to a second service, and the runner would still need the files.

### 2. Bare mirror cache + per-run checkout at a pinned commit
Sync does `git clone --mirror` (first time) / `git fetch --prune` into
`STATE_DIR/repos/<repository-id>.git`, holding a per-repository lock.
A run does `git --git-dir=<mirror> worktree`-free export:
`git archive <commit> | tar -x -C <run_dir>/project` (no `.git` in the run dir,
nothing to clean in the mirror). If the commit is missing from the mirror
(fresh volume), the runner fetches first. The run executes with
`project_dir = <run_dir>/project` and `playbook = <path>`.
*Alternative*: fresh shallow clone per run — simpler but slow and hammers the
remote; runs would not be reproducible if the branch moved.

### 3. Runs use the last synced commit, not branch head
The backend stores `last_commit_sha` on the repository and passes it in
`GitSource.commit`. Runs are reproducible and match what the UI shows; a user
who wants the latest code presses *Sync*. Recorded on `job_runs.commit_sha`.

### 4. Discovery: YAML files whose top level is a play list
Under `subdir` (default repo root), non-recursive into `roles/`,
`group_vars/`, `host_vars/`, `collections/`, `.github/`, the service parses
`*.yml|*.yaml` and keeps files whose top level is a list of mappings with
`hosts`, `import_playbook` or `ansible.builtin.import_playbook`. Returns
`{ path, content }` (content capped, e.g. 256 KiB) so the UI keeps showing the
playbook text without extra RPCs.

### 5. Data model (migration by the user)
- `playbook_repositories`: `id, name, url, branch (default 'main'),
  subdir, credential_id → credentials (set null), last_commit_sha,
  last_synced_at, last_sync_error, created_at, updated_at`.
- `playbooks`: `source text not null default 'inline'` (`inline|git`),
  `repository_id → playbook_repositories (cascade)`, `path text`,
  `missing boolean not null default false`; unique `(repository_id, path)`.
  `content` stays not-null (snapshot of the synced file).
- `job_runs.commit_sha text` (nullable).
Upsert by `(repository_id, path)` keeps playbook ids stable, so jobs survive
syncs. Files that vanish are flagged `missing` rather than deleted; running a
missing playbook fails with `PRECONDITION_FAILED`.

### 6. API
New `repositories` feature in `packages/api/src/v1/repositories/`
(`list, get, create, update, delete, sync`) following the standard
input/output/handler/router layering; `sync` maps gRPC errors
(`UNAVAILABLE`, `INVALID_ARGUMENT` auth/URL failures, `RESOURCE_EXHAUSTED`)
to oRPC errors and stores the message in `last_sync_error`. Playbook `update`,
`move`, `delete` reject `source = git` with `FORBIDDEN`. URL validated as
`https://…` or `ssh://…` / scp-like `git@host:path`; `file://` and local paths
rejected.

### 7. Proto
```proto
message GitSource { string url = 1; string commit = 2; string path = 3;
                    optional string private_key = 4; string repository_id = 5; }
message Playbook { string name = 1; string content = 2; optional GitSource git = 3; }
rpc SyncRepository(SyncRepositoryRequest) returns (SyncRepositoryResponse);
```
Backward compatible: inline runs leave `git` unset.

### 8. Frontend
Repositories render as folder-like cards in the playbooks browser (with a
Git icon, commit short sha, last sync time, sync button, error as
`InlineAlert`). Inside, Git playbooks reuse the existing definition with a
`read-only` badge and a hidden edit/move/delete. Repository create/edit uses
`FormDialog` with a credential `SegmentedPicker`/select.

## Risks / Trade-offs

- [Repo content is code executed against managed hosts, and an in-repo
  `ansible.cfg` in `project_dir` is honoured by Ansible] → export
  `ANSIBLE_CONFIG` to a runner-controlled file so the repo's `ansible.cfg` is
  ignored; keep `run/extravars.ts` rules; document that registering a repo is
  equivalent to granting playbook-authoring rights.
- [Malicious/huge repos filling the state volume] → size check after fetch
  (configurable `GIT_MAX_REPO_MB`), timeout on git commands
  (`GIT_TIMEOUT_S`), `--filter=blob:limit` not relied on.
- [SSH to the Git host uses the same `known_hosts`] → reuse
  `SSH_HOST_KEY_POLICY`; first sync with `accept-new` pins the key.
- [Sync and run on the same mirror concurrently] → per-repository
  `asyncio.Lock` + `git archive` is read-only; fetch is atomic on refs.
- [Sync counts against `MAX_CONCURRENT_RUNS`?] → no; separate small semaphore
  (e.g. 2 concurrent syncs).
- [Deleting a repository orphans jobs] → cascade deletes its playbooks, jobs
  get `playbook_id = null` exactly like deleting an inline playbook today.
- [Galaxy dependencies not installed] → documented limitation; runs that need
  them fail with Ansible's own error.

## Migration Plan

1. User generates and applies the Drizzle migration (defaults keep existing
   rows as `inline`).
2. Deploy Ansible image (with `git`) before or together with the backend; an
   old runner ignores the unknown `git` field, so the backend must not offer
   Git runs until the new runner is live (deploy together via compose).
3. Rollback: disable by not registering repositories; dropping the columns is
   a user migration.

## Open Questions

- ~~Should repository management be admin-only?~~ Decided: no, any

- ~~HTTPS token auth in the first version?~~ Decided: no; public HTTPS and
  SSH with a stored credential only.
- Optional "sync before run" toggle on jobs — deferred.
